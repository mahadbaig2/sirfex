# Phase 3.7 study authorization procedure

The current machine protocol is a **candidate** with `executable: false`. This document defines a future operating procedure; it does not approve or freeze the study. The matching-hash gate prevents accidental execution in the normal workflow. A self-supplied hash and JSON record are not cryptographic proof of independent human approval and do not protect against someone with unrestricted repository and filesystem access.

## Before any approval

1. Review the [candidate protocol](PHASE_3_7_CHECKPOINT_2_PROTOCOL_CANDIDATE.md), [Checkpoint 2A.1 report](PHASE_3_7_CHECKPOINT_2A_1_REPORT.md), exact controller hashes, development scenario identities, directed pairs, physical grid, search rule and resource limits.
2. Resolve every critical blocker documented in the report. Do not substitute a passing synthetic pilot for a real PPO budget estimate.
3. Obtain an explicit human decision on the exact protocol bytes and SHA-256. Record who approved it, when, and the approved identity separately from the protocol.
4. Only after that decision, create a frozen protocol with status `FROZEN — AUTHORIZED FOR EXECUTION` and `executable: true`, commit it, and record its full 40-character Git commit. Do not rewrite the approved commit.
5. Re-run the read-only dry run against the committed protocol and development manifest. Verify the controller inventory, manifest, work-plan digest, search-space hash and resource ceilings match the decision. Verify the working protocol bytes against `git show <commit>:<protocol-path>`.

## Separate machine-readable approval record

The operator must supply a distinct UTF-8 JSON file to `--authorization-record`. It is not generated by the execution command. It must contain:

```json
{
  "schema_version": "sirfex-study-authorization:1",
  "approval_status": "HUMAN_APPROVED",
  "approved_by": "<human identifier>",
  "approved_at_utc": "<timezone-aware ISO 8601 timestamp>",
  "protocol_sha256": "<approved protocol semantic SHA-256>",
  "frozen_commit": "<full Git commit>",
  "scenario_manifest_sha256": "<approved manifest semantic SHA-256>",
  "controller_inventory_sha256": "<semantic SHA-256 of controller_inventory>",
  "resource_limits_sha256": "<semantic SHA-256 of budget>",
  "work_plan_sha256": "<approved dry-run work-plan SHA-256>",
  "semantic_sha256": "<semantic SHA-256 of this record without this field>"
}
```

These placeholders are illustrative; **no real approval record has been issued**. The code validates the record's digest and its cross-references to the approved protocol, committed revision, manifest, inventory, budget and work plan. The record's `approved_by` and timestamp are operator assertions, not independently authenticated signatures. Keep the human decision in the project's review trail and verify it manually before invocation.

## Future approved invocation

After approval, use only the guarded CLI:

```powershell
sirfex robustness study --mode scientific-execute --protocol <frozen-protocol.json> --manifest <development-manifest.json> --approval-digest <human-approved-protocol-sha256> --authorization-record <independent-approval.json> --frozen-commit <full-commit> --output-dir <local-run-root>
```

Use `--mode resume` with the same identities and output root after a controlled stop. The runner stores a copy of the approval record and a machine-readable invocation request containing the actual paths, mode, commit and digests in the ignored local run directory. It rejects a changed approval record on resume. Review the run journal and cumulative budget before resuming; an unclean restart carries conservative time accounting and uncertainty. A budget extension requires a new reviewed plan and approval. Do not use a new record to bypass an exhausted frozen budget.

The current candidate is rejected before execution, even if someone supplies its own hash or a fabricated record. No full Phase 3.7 study is authorized by this document.
